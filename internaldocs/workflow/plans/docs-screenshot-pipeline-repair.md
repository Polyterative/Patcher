- 2026-07-24 — User-area harness bug fixes (found while validating the fallback against the real "Poly0" test account, which has genuine non-fixture data rather than only fixture rows):
  1. **Ancestor-attribute hidden-detection bug**: the existing fixture-hide loop's `element.closest(fixtureHideSelector)` places `data-docs-screenshot-hide="true"` on the nearest matching ancestor wrapper (e.g. `lib-clean-card`), which can be several DOM levels above the actual card element (`app-rack-micro`/`app-patch-micro`). The new fixture-retention logic was checking `card.hasAttribute(config.hideAttribute)` directly on the card element, so cards hidden via an ancestor were never recognised as hidden — this made real non-fixture cards register as "not visible" and blocked the gate even though 60 racks / 5 patches existed. Fixed by adding an `isHiddenInChain(start, container)` helper (mirrors the existing `unhideChain` ancestor walk) and using it for all card-visibility checks in the retention loop.
  2. **Stale `app-toolbar` selector**: `readCurrentAccountLabel()` first tried `app-toolbar a[href$="/user/area"]` to read the logged-in username, but no `app-toolbar` component exists in the app (the real component/tag is `app-wide-shell-toolbar`, confirmed in `app.component.html`). The selector silently matched nothing and fell through to a whole-`<h1>`-text-parsing fallback.
  3. **Polluted `<h1>` fallback text**: the user-area `<h1>` (`hero-content-card` template) concatenates `.title-main` + `.title-separator` + `.title-sub` (the actual username) + an optional `.title-inline-description` + an icon ligature all in one element, so `h1.textContent` produced strings like `"User area-Poly0Public profile is visible to everyone.dashboard"` instead of the clean username. Fixed by correcting the toolbar selector to `app-wide-shell-toolbar a[href$="/user/area"]` and adding a `h1 .title-sub` targeted read (checked before the old whole-`<h1>` fallback, which is retained as a last resort with an explanatory comment).
  4. **Heading-assertion dash/whitespace mismatch**: `validateUserArea`'s heading check used an em dash (`USER AREA — Docs screenshot account`) and `getByRole('heading', {name})`, but the live template renders a plain hyphen with no surrounding spaces and Playwright's accessible-name computation inserts newlines between the `<h1>`'s child spans. Fixed by matching a flexible `\s*-\s*` separator via a `page.locator('h1', {hasText: ...})` check instead of `getByRole` name matching.
  5. **DOM-presence vs. visible-content check for `[E2E]` text**: after the retention fix, up to ~2 fixture patch cards beyond the retained set remain in the DOM with `display:none` (correctly hidden from the screenshot) but still matched a raw `page.locator('text=/\\[E2E\\]/i')` DOM-presence check, which counts hidden elements too. Changed `validateUserArea`'s residual-`[E2E]`/`patcher-e2e-` checks to the existing `countVisibleTextMatches` helper (already used by `assertDocsSanitisation` for other targets), so the assertion matches what is actually visible in the published capture.
- 2026-07-24 — User-area validation: `node --test e2e/screenshots/__tests__/*.test.mjs` passed 6/6 after the `isHiddenInChain` fix. `pnpm test:e2e:screenshots -- --target=user-area` passed end-to-end (1 passed) after all fixes above. - 2026-07-25 — **New bug found and fixed after the full 10-target regression**: re-reviewing `01-home.jpg` post-regression showed the home page's fixed marketing "proof" patch (`HOME_PROOF_PATCH_ID = 5` in `home.component.ts`, a real, always-public patch shown to every site visitor regardless of auth state) with its title mutated from the genuine `"Demo Patch"` to `"Docs screenshot account"`. Root cause: the `readCurrentAccountLabel` `.title-sub` fallback added during the user-area fix (`682fe06e`) used an unscoped `document.querySelector('h1 .title-sub')`, but `hero-content-card` (which renders `.title-sub`) is reused across many unrelated pages/embeds — on `home` it picked up the embedded patch-details preview's `.title-sub` (`"Demo Patch"`, the patch's real name) and treated it as "the current account label," so the global text-replacement TreeWalker replaced every occurrence of that string anywhere on the page with the account-label replacement text. Read-only Supabase check confirmed no backend mutation occurred (`patches.id=5`.`name` is still `"Demo Patch"` in the database) — this was purely a client-side sanitisation-time text-corruption bug, not a data-integrity issue. Fixed by scoping the `.title-sub` read to only the `<h1>` whose `.title-main` text starts with `"USER AREA"`, so it can no longer match unrelated `hero-content-card` instances on other pages. Re-ran `node --test` (7/7 passed) and the full `pnpm test:e2e:screenshots` (10/10 passed) after the fix; `01-home.jpg` now correctly shows `"Demo Patch"`/`"Polyterative"` unchanged (matching the pre-existing, previously-committed baseline), and `08-user-area.jpg` is unaffected (still correctly scoped to the user-area heading).
